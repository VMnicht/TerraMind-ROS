## 3. 新电脑获取和构建

基准环境是 Ubuntu 22.04、ROS 2 Humble、C++17、系统 Python 3 和 PyQt5。以下步骤假设已安装 ROS 2 Humble desktop；工程不携带 ROS 安装包，也不携带其他机器的编译产物。

```bash
git clone https://github.com/VMnicht/TerraMind-ROS.git TerraMind
cd TerraMind
source /opt/ros/humble/setup.bash

# 首次配置机器时安装构建和依赖管理工具。
sudo apt install python3-colcon-common-extensions python3-rosdep
# 仅机器尚未初始化 rosdep 时执行一次：
sudo rosdep init
rosdep update
rosdep install --from-paths src --ignore-src --rosdistro humble -r -y

MAKEFLAGS="-j2 -l2" colcon build --symlink-install --parallel-workers 2 \
  --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo
source install/local_setup.bash
```

若 `rosdep init` 提示已初始化，继续后续步骤即可。依赖来源为各包的 `package.xml`；新增运行依赖时需更新它，不能只在个人机器上安装。Qt、rclpy 和 ROS 生成的 Python 消息使用系统环境，不建议混用 Conda 解释器。

新终端先加载 `/opt/ros/humble/setup.bash`，再加载当前工程的 `install/local_setup.bash`。一键脚本会自行完成这两步；缺少关键产物会自动构建。修改 C++、消息定义或 CMake 后仍须重新编译；已有构建产物并不表示源码变化已自动编译。

改动单个包时可按依赖构建，例如：

```bash
colcon build --symlink-install --packages-up-to terramind_mcu --parallel-workers 2
```

修改消息定义后建议完整构建工作区，并重启所有相关进程，使发布端和订阅端使用一致类型。

## 4. 开发运行入口

以下模式在同一个 ROS 域和命名空间中互斥。`start_panel.sh` 只开控制界面，不会替用户启动后端。

```bash
# 图形化管理构建、后端、测试和日志。
./start_debug.sh

# 完整二维仿真，默认含控制面板、模型和 RViz。
./start_sim.sh
# 修改源码后重新编译并启动。
./start_sim.sh --build
# 自动化环境中关闭图形窗口。
./start_sim.sh --headless
```

直接使用 ROS 命令时先加载环境：

```bash
# 二维仿真：当前板卡 47，全能力演示可设 63。
ros2 launch terramind_bringup sim.launch.py panel:=true capabilities:=47
# 虚拟串口：真实驱动连接临时 PTY。
ros2 launch terramind_bringup serial_test.launch.py panel:=true
# 实机：自动发现唯一控制板；不自动使能。
ros2 launch terramind_bringup real.launch.py panel:=true
# 手动指定端口时覆盖 auto。
ros2 launch terramind_bringup real.launch.py device:=/dev/ttyUSB0 panel:=true
```

上面的三条后端命令应选一种运行。同一个控制链路只使用一个上层控制源。多个机器人或模式对比需隔离 `ROS_DOMAIN_ID`，同一机器人各终端则使用相同的域。

串口访问出现权限错误时，检查 `ls -l /dev/ttyUSB* /dev/ttyACM*` 和当前用户组。Ubuntu 常见设备组为 `dialout`，可按机器实际情况加入该组后重新登录；不依赖长期以 root 运行节点。

## 5. 必须保持的行为约束

### 5.1 完整快照与三个层级的停机保护

1. 控制管理节点分别检查底盘与作业输入。使能后始终需要新鲜 `cmd_vel`；仅作业时也持续发布零速度。作业开启时还需新鲜 `implements/command`。
2. 后端 `CommandGuard` 独立检查完整快照，即使控制管理退出也会超时停机。停机锁定后须先接收未使能快照，再允许新的使能快照。
3. 下位机协议规定超过 250 ms 没有可接纳控制帧就将目标归零。仿真 `BoardModel` 模拟这一行为，但不能代替硬件验证。

默认 PC 指令和状态有效期均为 150 ms。控制管理及面板发送周期为 20 ms，板卡/模型状态约 50 ms。状态不是逐条控制命令的独立 ACK，服务响应也不是机械已执行确认。

### 5.2 时间与连接代次

`header.stamp` 使用 ROS 当前时间；实际超时用单调时钟。转换时扣除消息传输延迟，不能把到达时间作为新的完整有效期起点。控制消息检查过期、超前和倒序。

`connection_id` 是 PC 生成的随机非零连接代次，不是设备序列号或认证令牌。断连、板卡重启、仿真复位后旧指令不能继续生效。接管 USART3、握手就绪和允许运动是三个不同条件，端口打开不代表可以直接发送运动目标。

### 5.3 串口自动发现的边界

候选路径默认按 `/dev/serial/by-id/*`、`/dev/ttyUSB*`、`/dev/ttyACM*` 枚举，使用设备号去重。打开候选会设置串口参数并获取建议锁，但不发送识别字节。只有多帧有效状态的序号和 uptime 前进，且窗口结束时仍新鲜，才视为匹配。

恰有一个匹配才选择；多块控制板时要求显式 `device`。选中后保留已打开的句柄进入握手。协议 v1 没有设备唯一标识，因此这是协议识别，不是身份认证。自动发现依赖固件在接管前也主动上报状态。

### 5.4 面板与线程

控制面板的 ROS 回调、心跳和 Qt 界面共用同一线程。界面冻结后不能由后台线程继续发布旧运动目标。草稿只在开始或应用时校验并整体替换生效值；刷新反馈不应改变已发送目标。

使能状态机为 `idle → arming → waiting → running`。`arming` 先等待停止应答，再发使能；`waiting` 等待控制管理的使能反馈。停止递增 `generation`，使上一轮服务的迟到结果失效。关闭窗口先请求停止，再给异步处理留出短暂时间。

## 6. 参数与标定

| 配置文件 | 当前用途 | 主要参数 |
|---|---|---|
| [control.yaml](../terramind_bringup/config/control.yaml) | 控制管理、后端和面板共用 | `command_timeout_s=0.150`、`state_timeout_s=0.150`、`use_sim_time=false` |
| [serial.yaml](../terramind_bringup/config/serial.yaml) | 实机驱动 | `device=auto`、发现路径、监听 0.6 s、115200、发令 20 ms、重连 1 s |
| [sim.yaml](../terramind_bringup/config/sim.yaml) | 仿真模型和 URDF 尺寸 | 轮径 0.20 m、轮距 0.45 m、能力 47、线/角加速度限制 |
| [robot.yaml](../terramind_bringup/config/robot.yaml) | 真机标定记录，当前 launch 不加载 | 未知尺寸为 0、RPM 轴侧待确认、减速比待确认 |

配置中的能力掩码：`15/0x000F` 为底盘、左右播撒、刀盘；`47/0x002F` 增加喷洒；`63/0x003F` 再增加升降。实机只按板卡实际回传能力决定可控项，不能通过修改仿真配置让真实硬件获得新能力。

底盘速度单位为 m/s 和 rad/s。`ImplementCommand.left_rpm/right_rpm` 是播撒器，`ChassisState.left_*_rpm/right_*_rpm` 才是底盘轮速。真实轮速轴侧和反馈新鲜度尚未完全定义，不能直接拿仿真轮径算实机里程计。

## 7. 修改功能时从哪里入手

### 新增或调整作业字段

1. 先确认下位机协议的 TLV、单位、范围、能力位、停机值和反馈有效性。
2. 更新 `terramind_interfaces/msg`；新增消息文件还要登记到对应 `CMakeLists.txt`。
3. 更新协议结构、编解码及数值校验，不要直接序列化 C++ 结构体内存。
4. 更新 `ros_helpers.hpp`、`ros_conversions.hpp`、控制管理和模型的字段映射。
5. 更新面板 `ACTUATORS`/`Selection` 和反馈展示，区分目标与实测值。
6. 覆盖正常控制、关闭归零、越界、能力缺失、超时停机和旧板卡兼容测试。

仅把已有装置接到板卡、不改变协议布局时，仍需按实际反馈确认能力位。不要擅自改变 v1 已有字段或帧长度。

### 接入新的上层控制算法

发布 `TwistStamped` 和完整 `ImplementCommand`，每周期使用新时间戳；通过标准使能/停止服务管理会话。算法不直接发布 `mcu/command`。当前没有多源仲裁，若同时接入遥控、自动导航和面板，需要先设计明确的控制权切换与失效处理。

### 后续组合导航板

建议新增 `terramind_navigation_driver`，保留独立端口、协议解析、重连与诊断。传输库当前只允许 115200，如果新板卡波特率不同，需要扩展库并增加测试，而非绕开串口占用锁。

协议确定后再选择 `sensor_msgs/msg/NavSatFix`、`sensor_msgs/msg/Imu`、`nav_msgs/msg/Odometry` 等输出；明确坐标系、单位、采样时间、时间同步、协方差和反馈有效性。导航协议、导航驱动和定位融合当前均未实现。

### 后续物理仿真

可保留上层 ROS 接口和板卡行为边界，用物理引擎替换差速运动模型。当前模型无碰撞、坡面或轮胎打滑，使用真实时间且不发布 `/clock`。接入 Gazebo 或可暂停仿真前，需要先定义暂停、时间回跳、超时和重新使能策略，不能只把 `use_sim_time` 改成 true。

## 8. 测试和提交

完整命令与覆盖范围见 [联调与测试说明](联调与测试说明.md)。常规修改至少执行相关包测试并检查结果：

```bash
colcon test --event-handlers console_direct+
colcon test-result --verbose
```

修改协议增加独立 Python 字节回环；修改控制状态机增加 ROS 链路测试；修改面板增加 Qt 集成测试；修改调试启动器验证进程组退出和构建后启动。新增测试应覆盖行为和失效边界，而非只重复实现公式。

提交前执行 `git diff --check`、检查 `git status` 和差异。源码、消息、配置、脚本、文档入库；`build/`、`install/`、`log/`、缓存及录制数据不入库。源码注释使用中文说明“为什么”和约束，保留协议字段、ROS 类型和 API 标识的原名；不要把未来计划写成已实现行为。

## 9. 排查入口

| 现象 | 优先检查 |
|---|---|
| 面板持续等待状态 | 后端是否启动、环境是否正确加载、ROS 域/命名空间是否一致 |
| 自动发现不到控制板 | 端口权限、其他进程占用、主动状态帧、115200 8N1、`/diagnostics` |
| 多个控制板拒绝连接 | 通过 `device:=...` 明确指定，不以枚举顺序决定设备身份 |
| 使能后很快停止 | `/control/status.reason`、两路输入的新鲜时间戳、板卡 result/faults |
| 作业控件不可用 | `/mcu/state.capabilities`；反馈有效性与是否支持是两个判断 |
| Snap 的 GLIBC_PRIVATE 错误 | 通过一键脚本启动，或先 source `scripts/native_gui_env.sh` 再加载 ROS |
| RViz 无模型或不能平移 | `robot_description`、TF、固定坐标 `sim_world`、Move Camera 和 Orbit |
| 总面板显示进程运行但链路未就绪 | 进程启动不等于协议握手成功，继续查看控制面板和诊断 |

```bash
ros2 node list
ros2 node info /control_manager
ros2 topic list -t
ros2 topic echo /control/status
ros2 topic echo /diagnostics
ros2 interface show terramind_interfaces/msg/McuState
```
